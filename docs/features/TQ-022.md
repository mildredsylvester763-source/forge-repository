# TQ-022: Interruption scenarios

## Behaviour

- Seven interruption scenarios exist: incoming-call, incoming-sms, push-notification, low-battery, network-drop, app-background and system-update, each with a resume policy and a data loss risk flag.
- The catalog filters per platform: web keeps push-notification and network-drop, desktop keeps four, watch supports none.
- A live interruption is ruled in order: platform, scenario, platform support, then session status (only running sessions can be interrupted).
- Interrupting pauses the session, records a step and emits SessionStatusChanged when resume is manual.
- Refusals are named: interruption-platform-missing, interruption-platform-unknown:X, interruption-scenario-missing, interruption-unknown:X, interruption-platform-unsupported:S:P, interruption-status-missing, interruption-session-not-running:X.

## Where it lives

src/modules/live-testing/engine/interruption-scenario.ts (pure), POST /v1/live-testing/interruptions for the catalog and POST /v1/live-testing/sessions/interrupt for the live verdict.

## Limits, stated plainly

Interruptions are simulated against the session state machine; no phone calls are placed and no OS events are received.
