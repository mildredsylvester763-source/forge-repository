# TQ-031: Unit test generation

## Behaviour

- A unit suite is planned from the target signature (function or class) plus declared behaviors: boundary value analysis per parameter (empty, single, many for strings and arrays; 0, 1, -1 for numbers; true, false for booleans; empty, one key for objects) plus exactly one case per declared behavior. Limits: 10 parameters, 20 behaviors.
- Boundary cases are named boundary:parameter:type:index with rendered details (str(n), arr(n), obj(n), plain values for numbers and booleans); behavior cases are named behavior:name.
- Malformed input is refused by name: unit-target-missing, unit-target-name-missing, unit-target-name-too-long, unit-target-kind-unknown:x, unit-params-limit:n, unit-param-name-missing, unit-param-type-unknown:x, unit-param-duplicate:x, unit-behaviors-empty, unit-behaviors-limit:n, unit-behavior-name-missing, unit-behavior-duplicate:x.

## Where it lives

src/modules/test-generation/engine/unit-test-generation.ts (pure), reached through POST /v1/test-generation/unit/plan. GET /v1/test-generation/unit/kinds and GET /v1/test-generation/unit/param-types list the catalogs.

## Limits, stated plainly

Boundary analysis covers declared parameter types, not runtime values: it plans the boundaries the market proved worth testing, it does not read the code body.
