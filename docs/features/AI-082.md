# AI-082: Task history journal and replay

## Behaviour

- Thirteen event types (task-created, step-started, step-validated, step-completed, step-failed, gate-requested, gate-resolved, task-paused, task-resumed, task-cancelled, task-completed, task-failed, takeover) form an append-only journal with contiguous sequence numbers 1..n.
- Appending validates the whole journal first; broken journals are refused by name (history-seq-gap:1:2, history-event-invalid:2, history-type-unknown:teleport).
- Replay folds the journal to the derived state plus step and gate ledgers that update in place. An empty journal is a task that applied nothing.
- Replay can stop at any toSeq; out-of-bounds or fractional values are refused as history-to-seq-invalid.

## Where it lives

src/modules/task-runtime/engine/task-history.ts (pure), persisted per run in task_runs.events (SQLite TEXT JSON, PostgreSQL JSONB), reached through POST /v1/tasks/runs, POST /v1/tasks/runs/event, POST /v1/tasks/runs/replay and GET /v1/tasks/runs.

## Limits, stated plainly

The journal is the truth; the stored state column is a cache of the last replay. List responses are capped at the latest 50 runs per user.
