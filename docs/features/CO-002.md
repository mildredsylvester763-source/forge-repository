# CO-002: Passkeys / WebAuthn

**Implementation status:** backend ceremony, credential lifecycle and native/browser completion paths implemented provisionally. Focused verification passed. Feature-level owner acceptance and production activation remain open.

## Implemented backend capability

- Generates cryptographically random challenges and stores only SHA-256 challenge hashes. Challenges are purpose-bound (registration/authentication), owner-bound for registration, expire after two minutes, and are consumed once with atomic store operations.
- Supports in-memory, SQLite and PostgreSQL store adapters for challenge and credential records.
- Registration options are available only to authenticated users. Completion validates the client challenge and exact relying-party origin relationship, verifies supported WebAuthn attestation/credential data, and stores the credential public key and authenticator metadata.
- Authentication options are discoverable. Completion verifies credential ID, signature, challenge, origin, RP-ID hash, user-presence/user-verification flags, user handle, backup flags and authenticator counter behavior.
- Credential listing and removal are owner-scoped. Public responses omit stored public-key material. A credential record cannot be removed by another account.
- Credential creation, authenticator counter updates and removal are coupled to audit events. SQLite and PostgreSQL perform the state change and event append in one database transaction. The in-memory store serializes mutations.
- Passkey ceremonies have a dedicated per-IP throttling bucket, separate from password sign-in. The current implementation is in-memory and therefore does not establish shared multi-replica enforcement.
- RP configuration is optional until deployment supplies both `FORGE_WEBAUTHN_RP_ID` and `FORGE_WEBAUTHN_ORIGINS`. When set, startup validates the pair and fails closed for invalid or mismatched values.
- Browser authentication completion sets the normal session cookie. Native completion returns the same opaque server-managed session as a bearer token and does not set a browser cookie.

## HTTP surface

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/v1/auth/passkeys` | List the authenticated user's public passkey metadata |
| POST | `/v1/auth/passkeys/registration/options` | Issue a registration challenge |
| POST | `/v1/auth/passkeys/registration/complete` | Verify and register a credential |
| POST | `/v1/auth/passkeys/authentication/options` | Issue a discoverable authentication challenge |
| POST | `/v1/auth/passkeys/authentication/complete` | Authenticate and set a browser session cookie |
| POST | `/v1/auth/native/passkeys/authentication/complete` | Authenticate and return a native bearer session |
| POST | `/v1/auth/passkeys/remove` | Remove an account-owned credential |

## Protocol and data boundaries

- The supported attestation mode is `none`; this verifies the credential proof but does not establish authenticator model or hardware provenance.
- Supported COSE signing algorithms are ES256, Ed25519 and RS256. Input parsing is bounded and rejects malformed base64url, CBOR, client data and authenticator data.
- Credential IDs are identifiers, not bearer credentials. Session bearer values are generated separately and only their hashes are stored.
- A zero authenticator counter is handled according to WebAuthn counter semantics; non-zero counters must advance monotonically.
- The PostgreSQL adapter is implemented but still needs a real PostgreSQL-backed CI run. The focused workflow currently verifies typecheck and the local/in-memory/SQLite regression path.
