# CO-001: Email and password sign-in with breached-password checks

## Behaviour

- **Register**: normalises the email, applies the password rules, checks the breach services, hashes, stores, emits an event.
- **Sign in**: throttles, verifies in constant-ish time, re-checks the password against breaches, prepares a session, and emits an event. A password-hash upgrade, session insertion, per-user session-cap enforcement and sign-in event are committed together by the identity unit of work.
- **Sign out / me**: sign-out revocation and its completion event are committed together; read the current session.
- **Compromised-password detection**: the account security flag and its detection event are committed together. Repeated detections do not create duplicate state-transition events.
- **Session cap**: the configured per-user maximum is enforced inside the same unit of work as sign-in. Concurrent sign-ins serialize per user; the least recently active sessions are retired deterministically before the new session is committed.

## Password rules (NIST 800-63B)

12 to 128 characters, any characters allowed (spaces and Unicode included), no forced symbols or digits. Rejected: control characters, one repeated character, passwords containing the account email, anything in a known breach.

## Breach checking

Two layers: an instant local blocklist, then the Have I Been Pwned range API with padding.

If the breach service is unreachable:
- `fail-closed` (default): registration returns 503. Safer.
- `fail-open`: registration proceeds and a `breach_check_skipped` event is recorded.

Sign-in never fails because of the breach service. If the check cannot run, sign-in proceeds.

## Limits, stated plainly

SQLite storage is durable for a single-server deployment. A PostgreSQL adapter and transactional unit-of-work implementation exist, but a real PostgreSQL CI run and production deployment have not yet been evidenced in this workstream. No email verification. No password-change endpoint yet, so `passwordChangeRequired` is a flag the client can show. Session tokens are cookie-only (browser). Tokens for the Android and desktop clients arrive with CO-007 and CO-009.


## Transactional guarantees added on the Mistral branch (2026-11-05)

- Registration and sign-in session creation use the existing unit-of-work pattern for state plus event writes.
- Sign-in now enforces the active-session cap inside the transaction. SQLite uses a write transaction; PostgreSQL locks the user row before reading and retiring sessions. In-memory development storage serializes by user key.
- Sign-in hash upgrades, session creation, session-cap revocations and the success event roll back together on event failure.
- Sign-out revocation and its completion event roll back together; repeated sign-out is idempotent.
- Password-compromise state and its detection event commit together and emit only once per transition.
- Verification tests are committed in `test/co-065-atomic-signout.test.ts` and `test/co-065-postgres-uow.test.ts`. They are not considered passed until the CO-focused CI workflow completes successfully. A real PostgreSQL run requires `FORGE_TEST_POSTGRES_URL`.
