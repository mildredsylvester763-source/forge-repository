# CO-003: Social identity provider sign-in

**Implementation status:** partial, provider-neutral OIDC authorization and verified-token callback engine. No external provider has been selected or activated; account linking, FORGE session issuance and production social sign-in are not claimed.

## Implemented foundation

- Validates a configured provider key, issuer URL, authorization endpoint, client ID, redirect URI, environment and OIDC scopes.
- Production endpoints require HTTPS; HTTP is permitted only for loopback development/test endpoints. URL credentials and fragments are rejected. The required `openid` scope must be present.
- Creates independent cryptographically random OAuth state, OIDC nonce and PKCE verifier values.
- Uses PKCE S256, authorization-code response type, an exact configured redirect URI, and an explicit scope list.
- Stores SHA-256 hashes of state and nonce. The raw code verifier is retained only in the in-memory server-side transaction store and is never returned by the authorization-start operation.
- Callback state consumption is one-time. Expired, replayed and wrong-provider state is rejected; a wrong-provider callback burns the state rather than leaving a transaction reusable.
- The provider-neutral module does not hard-code Google, GitHub, Apple or any other provider.
- Validates OIDC discovery metadata, including exact issuer matching, HTTPS endpoints, authorization-code support, public subject identifiers, supported signing algorithms and supported token-endpoint client-authentication methods.
- Exchanges authorization codes server-side using the original PKCE verifier, exact redirect URI and optional server-held client secret. Redirect following is disabled, requests use no-store headers and responses are size-bounded.
- Fetches bounded JWKS documents and rejects duplicate key IDs. Verifies ID-token signatures for RS256, PS256, ES256 (JOSE IEEE-P1363) and EdDSA/Ed25519.
- Validates exact issuer, client audience, authorized party, expiry, issued-at, not-before and transaction nonce. The returned subject is provider-scoped; an email claim is explicitly marked verified only when `email_verified === true`.
- `OidcAuthenticationService` consumes one-time state before network activity, performs code exchange, retrieves signing keys and returns only a verified OIDC identity. Replayed state is rejected before another provider request.

## Deliberate non-implementation boundary

- No provider has been selected, configured or granted credentials.
- No callback HTTP route or userinfo retrieval is implemented. Discovery/JWKS retrieval, ID-token signature validation, issuer/audience/nonce claim validation and authorization-code exchange are implemented as provider-neutral services.
- No external provider subject is linked to a FORGE account, and no account is auto-created from an unverified email.
- The transaction store is in-memory only. It does not provide multi-instance continuity or survive process restart. The verifier must not be moved to persistent storage until an approved encryption/key-custody design exists.
- The verified-identity service does not link a provider subject to a FORGE user, auto-create accounts, or issue a FORGE session. An authorization URL is not proof of an authenticated identity; only the callback verifier's returned identity has passed the OIDC checks.

## 2026-11-10 discovery-binding verification update

The latest CO-003 hardening on Mistral adds an issuer-discovery check before authorization begins and repeats it before the callback token exchange. The discovered authorization, token and JWKS endpoints must exactly match the configured provider endpoints. Token exchange and JWKS retrieval use the validated discovery metadata, and ID-token verification now rejects any signing algorithm that is not advertised by that provider's discovery document.

The implementation remains **PARTIAL**. The OIDC services are not wired into `src/app.ts` or `src/config.ts`; there is still no callback HTTP route, linked-provider identity store, account-resolution/session-issuance path, or durable OIDC transaction store. Identity SQLite and PostgreSQL migrations are at version 8 and contain no OIDC transaction or linked-subject tables. The transaction adapter remains in-memory. No provider has been configured or activated.
