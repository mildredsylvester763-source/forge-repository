# TQ-023: Permission matrix

## Behaviour

- Each platform has its own permission vocabulary: web 5, android 7, ios 7 and desktop 5 permissions, all named in the catalog.
- A permission plan stages the pre-session state: a list of permission and state pairs with states ask, granted or denied, plus granted, denied and ask counts.
- Runtime choices walk the state machine: ask with deny becomes denied (still askable), denied with deny becomes blocked, granted with deny becomes denied (askable again), and blocked never prompts again.
- Refusals are named: permission-platform-missing, permission-platform-unknown:X, permission-plan-not-array, permission-plan-empty, permission-grant-not-object, permission-name-missing, permission-unknown:P:F, permission-state-missing, permission-state-invalid:X, permission-state-not-planable:blocked, permission-duplicate:P.

## Where it lives

src/modules/live-testing/engine/permission-matrix.ts (pure), POST /v1/live-testing/permissions for the catalog and POST /v1/live-testing/sessions/permissions to apply a plan (requires the control capability; terminal sessions refuse with permission-session-terminal).

## Limits, stated plainly

Permissions are simulated for test design; no OS permission dialogs are shown and no real permission state is read.
