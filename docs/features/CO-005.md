# CO-005: Multi-factor authentication

**Implementation status:** partial, TOTP enrollment/confirmation, encrypted secret persistence and replay-safe verification primitives are implemented. Account enforcement, recovery and production key management are not implemented.

## Implemented backend foundation

- Generates cryptographically random TOTP secrets (20–64 bytes), canonical Base32 values and RFC 6238 codes using explicitly injected SHA-1/SHA-256/SHA-512, 6/8 digit and 15–120 second options.
- Verifies codes in an explicitly configured 0–2 step window using constant-time comparison and returns the matched moving factor.
- Starts pending enrollment with a bounded expiry and returns the secret/provisioning URI once for the authenticated client to display. The stored secret is AES-256-GCM encrypted; the 256-bit encryption key is injected and never stored in the database.
- Binds ciphertext authentication to the user ID using AEAD associated data. Wrong key, corrupted ciphertext or altered user binding fails closed.
- Requires confirmation with a valid TOTP code before activating a factor. The confirmation step is immediately recorded as consumed, so the enrollment code cannot be replayed for sign-in.
- Verifies active factors and atomically advances the greatest accepted moving factor with compare-and-swap. Concurrent submissions of the same code can succeed only once.
- Supports cancellation of pending enrollment and disabling an active factor only after a valid, newly consumed code.
- Adds SQLite and PostgreSQL factor stores and identity migration v4. A user can have one pending or active TOTP factor in this implementation.
- Tests include RFC 6238 published vectors, Base32 handling, encryption-at-rest checks, enrollment expiry/confirmation, wrong-key failure, concurrent replay attempts and one-time moving-factor consumption.

## Deliberate non-implementation boundary

- No HTTP enrollment/confirmation/disable routes are mounted and no TOTP step-up challenge is wired into password/passkey sign-in. The crypto and storage service does not by itself enforce MFA for an account.
- No recovery/backup codes, lost-device recovery, administrator reset, email/SMS delivery, rate-limit policy or security notification workflow is implemented.
- No production encryption key source is wired. The service requires a 32-byte key injected at construction; no key is generated, persisted or committed by this feature.
- The PostgreSQL adapter and migration are implemented but have not been exercised against a live PostgreSQL service. Focused CI exercises SQLite.
- No default MFA policy is assumed. The product must decide whether MFA is optional, mandatory, tenant-enforced or step-up-only before login enforcement is enabled.
