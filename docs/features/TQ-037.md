# TQ-037: Contract testing

## Behaviour

- A pact is a collection of concrete request/response interactions the consumer exercised, built with normalized methods (uppercase) and paths (single leading slash, collapsed duplicates).
- Provider verification replays each interaction against recorded provider responses and checks route, status and body. The expected body is a deep subset of the actual body: extra provider keys are allowed, missing or unequal expected keys are violations.
- Malformed input is refused by name: contract-consumer-missing, contract-consumer-too-long, contract-provider-missing, contract-provider-too-long, contract-interactions-empty, contract-interactions-limit:n, contract-description-missing:i, contract-method-missing:i, contract-path-missing:i, contract-status-missing:i, contract-status-invalid:i:x, contract-responses-missing, contract-response-method-missing:i, contract-response-path-missing:i, contract-response-status-missing:i, contract-response-status-invalid:i:x, contract-route-missing:i:method:path, contract-status-mismatch:i:expected:actual, contract-body-mismatch:i:path.

## Where it lives

src/modules/test-quality/engine/contract-testing.ts (pure), reached through POST /v1/test-quality/contract/build and POST /v1/test-quality/contract/verify.

## Limits, stated plainly

Verification compares recorded responses, not a live provider. Subset matching means a provider returning more than the pact is still verified; it cannot detect a consumer that expects too little.
